# Carbon effect JSON format plan

Status: Evolving
Visibility: Public-safe design proposal
Scope: Shader authoring library in tools-shader and its planned runtime resource Format integration
Audience: Director, runtime resource maintainers and Carbon effect tooling authors
Summary: Import a readable JSON mirror of the Carbon effect container, using Carbon names, complete stage declarations, a source-agnostic program slot and isolated browser metadata.

## Decision and implementation gate

The starting point is a **readable JSON mirror of the Carbon effect container**. The container contract defines its content and permutation behavior; `trinity/shadercompiler/EffectData.h` supplies Carbon's names, nesting and types for its effect bodies. Where our reader renames a field, authored JSON uses Carbon's name. This is a container authoring format, not a serialization of the compiler's entire working state.

This direction supersedes the compiler-EffectData-only revision. Do not require compiler-process handles, debug source, PDB blobs or other unsaved compiler members just to author browser effects. Counts, arena addresses and packed sizes are generated by the existing writer. The field ledger below distinguishes persisted content from its JSON representation.

The immediate consumers need readable JSON shader assets. Future Carbon effect tooling must be able to reuse the same format when Carbon's HLSL shaders become available. GLSL and WGSL are the first executable program languages. HLSL and compiled bytecode must fit the same program slot later, without creating another Format. Accepting or preserving an HLSL payload is distinct from being able to compile it.

Implement only the resource Format, its necessary exports/tests/docs and its explicit registration helper. Do not alter the renderer, native donor, existing binary contract or unrelated runtime services. Any integration problem requiring a wider change returns to review. The shader authoring library lives at the organization root in `tools-shader/`, with this plan in `tools-shader/docs/`. It consumes the runtime resource Format and shares its schema. The library home is confirmed; the Format names below still require review.

The non-Carbon addition is recorded in the organization extension register. Required consumers are selection outlines and technical lines. **The names below are the complete proposal submitted for director review, not permission to implement.** No implementation starts until the director has reviewed the final names. This document change is committed by explicit path and is not pushed.

Excluded from this container mirror because native Save does not emit them: `Sampler.filter` (442), `Sampler.srgbTexture` (456), `StageInput.source` (716), `Library.source` (784), and `EffectData.pdbs` (851; PDB fields at 813–815). They do not become required authoring fields or a PDB implementation task.

References such as `StringReference` are compiler-process handles, not JSON addresses. Names become text at their existing field sites. The adapter interns names, defaults and program bytes and creates the references needed for writing. The readable input omits generated `shaderSize` and `defaultValuesStr` handles; the adapter derives the byte count and arena reference from the payload and `defaultValues`. These are representation adaptations, not renamed Carbon members.

Vectors become arrays. `std::map` becomes a JSON object with canonical decimal numeric keys or text keys as appropriate. Validate key range and canonical numeric spelling; define and test rejection of duplicate object keys at the JSON input boundary. Preserve numeric map ordering and Carbon's bytewise annotation-name sorting at serialization. Byte arrays contain integers 0–255. No metadata is lifted from stages into a shared top-level parameter table.

JSON cannot represent every native floating-point bit pattern. The director must review a lossless encoding before implementation: proposed exceptional numeric values use `{ "bits": uint32 }` at the existing float field, while ordinary finite values use JSON numbers. This encoding is a new JSON representation, not a Carbon field. Apply it consistently to defaults exported as typed values, sampler floats and annotation unions. Packed `defaultValues` initially stays a byte array. A bytes-to-JSON-to-bytes test must cover negative zero, infinities and NaN payloads before any byte-exact export claim.

## Header and permutation field sources

The [container contract](../resource/formats/carbon-effect-container.md) owns header layout and runtime permutation selection. The following field citations refer to native `trinity/shadercompiler/ShaderCompiler.cpp`.

| JSON field | Native source | Meaning in this container mirror |
|---|---|---|
| `version` | 822–823; EffectData.h:10 | Container DATA_VERSION; initially write v15 through the existing writer. |
| `shaderCompilerVersion` | 825; ShaderCompilerConfig.h.in:5 | Four compiler-version bytes, using the container contract's field spelling. Generated provenance identifies this importer, not a fictional CCP compiler run. |
| `sourceHash` | 827–828 | The header's 32 ASCII hash characters. The hashing policy for newly authored JSON is specified with the Format; this is not an integrity guarantee. |
| `permutations` | 769–795 | Ordered axis records; the JSON list replaces count/offset bookkeeping. |
| Axis `name` | 772 | Text from native Permutation.name (ParserState.h:183). |
| Axis `defaultOption` | 774–782 | Default **option index**, as stored in the container. Validate that it selects an existing option. |
| Axis `description` | 783 | Text from native Permutation.description (ParserState.h:186). |
| Axis `type` | 786 | Native permutation type byte (ParserState.h:187); ParserState.cpp:546–560 defines static/dynamic interpretation. |
| Axis `options` | 789–794 | Ordered option names, as stored in the container. |
| `bodies` | 763–819, 833–844 | Proposed readable array, one complete body per logical permutation ordinal. The writer computes dense records, addresses and byte-identical alias sharing. No physical offsets are authored. |

Retain Carbon's axis and option order, default behavior and enumeration: the first axis varies fastest (ShaderCompiler.cpp:448–498). Require complete coverage, with one body for an effect with no axes. Identical bodies may be repeated in input and are deduplicated by the current writer. Do not add another alias/reference vocabulary to the first version.

The compiler has additional source-stage information in ParserState.h:175–191: a named default, numeric `PermutationOption.value`, and source location. The container writes a default index and option names and does **not** retain those macro values or locations. The initial JSON mirror follows the container representation. Document that distinction; a later HLSL tool must supply explicit compile-time values when needed, not assume option ordinals reconstruct native macro values. This is future authoring metadata within the same Format, not a reason to replace the current permutation model.

Use native enum assignments and names from EffectData.h: `InputStageType` (14–22), `ConstantType` (24–31), `AnnotationType` (35–41), `TextureType` (43–70), `UsageCode` (72–83), `RegisterInputType` (88–116), and `RtShaderType` (118–125). Numeric JSON values retain those assignments. Any later symbolic input must use those exact identifiers. Raw sampler/state numeric fields stay in their native domains.

## Source agnostic program slot

Proposed program slot, for review:

```json
"shaderDataStr": {
  "language": "wgsl",
  "target": "webgpu",
  "payload": "@fragment fn main() -> @location(0) vec4<f32> { return vec4<f32>(1.0); }"
}
```

This replaces a process-local program `StringReference` with a described payload at the same member. `language`, `target` and `payload` are explicit format extensions. Their shape remains the same for `glsl`, `wgsl`, future `hlsl`, and future compiled-bytecode values such as `dxbc` or `dxil`. Text payloads are strings; the proposed compiled payload representation is a byte array. Exact future target/profile values must come from the implemented compiler/backend, not assumptions in this plan.

Initial executable pairs are GLSL for the WebGL2 target and WGSL for WebGPU, under the current backend conventions. WGSL uses the existing `main` entry point. A future HLSL producer fills the same slot and supplies or invokes a compiler adapter to produce the native program bytes and reflection. Until then, structural inspection can report an HLSL payload while executable read fails with an unsupported compiler/language diagnostic. It must never encode HLSL text as if it were executable DXBC.

Keep native `StageInput.source` and `Library.source` distinct: native Save omits those debug strings. Do not repurpose them into the portable program slot or invent stage-specific `vs`/`ps` containers.

## Browser extension boundary

The optional extension member `browser` contains `webgpu` and/or `webgl` branches. Shared container header/permutation declarations stay outside that extension. Each branch's `bodies` contains complete container bodies with the Carbon field structure above. Its `backendBlocks` holds the pass binding metadata separately, indexed by permutation, technique index and pass index. The metadata's existing backend-specific records are passed to the existing codecs; they are not copied into native Pass or StageData.

Top-level `bodies` is the ordinary container body list. A browser-only document may omit it and provide browser branches instead. Native tooling can ignore `browser`; if no top-level bodies remain, it reports that the document has no native effect implementation rather than trying to interpret a browser branch. A bundle may carry all branches. There is no implicit inheritance or patch-merging between branches.

Browser programs and their `target` values therefore live inside the optional browser branch; shared program-descriptor vocabulary remains source-agnostic. Compare language/target against the explicitly requested output. A future HLSL tool does not need WebGPU binding groups, WebGL texture/sampler pairings, or backend-block knowledge to inspect the ordinary container contents.

One emitted container still targets one backend. Reuse the current `writeBackendBlock` and `writeGlslBackendBlock`; validate their bindings against each stage's explicit declarations. Do not infer reflection from arbitrary GLSL/WGSL or derive all backend interfaces from a shared parameter list. Preserve constants, textures and sampler descriptors exactly where Carbon owns them.

## Writing path and declared differences

Read the JSON mirror, validate Carbon-shaped body records and map them privately to the existing container codecs. Do not introduce a public EffectData compiler intermediate or serialize compiler working state. The ledger below records the authoring adaptations and existing writer mapping; it does not require implementing the native compiler.

| Enumerate permutations | `AddPermutationsToWorkQueue`, ShaderCompiler.cpp:448–498 | Preserve container axis/option order and body ordinals; read resolved bodies instead of invoking compiler workers. Source macro values are not reconstructed. |

The existing JS writer collects arena entries before final offsets and packs through its shared codec rather than literally instantiating native streams. Reuse that established algorithm; verify equivalent serialized output and document it as the implementation adaptation. No second binary writer is needed.

## Format registration and scope

Implement the normal `CjsFormat` contract in runtime resources: identity, dedicated extensions, declared outputs, cheap identification/inspection, normal read methods and inherited async entry. Use byte acquisition and `outputStreams: 0`. CPU inspection is not GPU verification. Direct module import must remain decorator-free and must not register global state.

The proposed `RegisterCarbonEffectJsonResources` helper explicitly registers the Format and routes its extension to `Tr2EffectRes` through existing `RegisterFormat` and `RegisterExtension` APIs. An explicit route owns its own defaults; do not assume it inherits a separate format registration's defaults. Do not send these authored inputs through the compiled-DXBC translator in `RegisterShaderResources`.

Include target output in the existing request/variant identity. Verify cached WebGPU and WebGL results cannot alias, that release/reload retains the chosen output, and that the normal effect facade reaches the registered extension. `ResolveEffectPath` currently rewrites `.fx` only; the dedicated extension must preserve that behavior. Registration defaults can bind the target for an application. If existing request composition cannot express a required target, bring that precise gap to the director; this plan does not authorize changing the engine/resource architecture.

## Implementation sequence and acceptance

1. **Director review before code.** Review the names table, program descriptor, container/browser representation, exceptional float encoding and source ledger. Confirm extension-register status. Do not begin a Format implementation on the basis of this proposed plan alone.
2. **Specify and fixture the approved contract.** Add a complete JSON fixture using native names and enums, all stage declarations, parameter annotation wrappers, and multiple named permutation options with a nonzero default index. Include browser implementations and a reserved HLSL descriptor to prove the same slot can be recognized without claiming compilation support.
3. **Implement the bounded Format and helper.** Validate JSON, resolve the chosen branch, map the JSON body records to the existing writer, and register normal resource loading. Keep mapping private and all browser additions explicitly isolated. Errors identify language/target, permutation, technique, pass, stage and field.
4. **Verify serialized fidelity and resource behavior.** Test all field mappings, enum values, map ordering, annotation union bits, byte defaults, exclusion of unsaved compiler fields, default-option indices, option names/order, complete enumeration and deduplication. Load through the real manager; check named selection, cache separation, byte retention and reload. Compare binary records against the expected native Save sequence without claiming a native-compiler build ran.
5. **Verify executable browser behavior.** Compile/link and draw a synthetic effect on both backends. Exercise a constant, texture, sampler, vertex input, render-state change and both named permutations. Confirm unsupported HLSL/bytecode execution and unsupported stages fail explicitly. No shipped shader tier is qualified by this synthetic test.
6. **Document and adopt.** Publish supported Format/registration documentation, retain donor citations per field in the schema mapping, run focused applicable checks, and adopt it for outline and technical-line effects. Native HLSL compilation and richer authoring tools are later extensions through the same program slot.

Acceptance requires both a readable, Carbon-shaped container mirror and a registered browser draw with correct bindings. Packaging strings alone is insufficient. Scope remains the Format and its registration helper, including their exports, documentation and tests. Commits use explicit paths; no push is authorized.

## Evidence and limits

The earlier synthetic probe showed that existing browser container writers/readers can carry GLSL/WGSL strings, two named variants, stage annotations and states. It used no bound resources and no GPU execution. It establishes feasibility of the original container-mirror direction, not a finalized JSON schema or correct GPU bindings. Its ad hoc input is not a normative fixture.

The native compiler source provides a standalone CMake project, but a successful local compiler build was not obtained. This plan makes no claim that HLSL compilation is available. The initial Format requires neither the native compiler nor an HLSL-to-browser translator.

The existing model/writer are Carbon; readable JSON encoding, the program descriptor and separated browser fields are our declared extension.
